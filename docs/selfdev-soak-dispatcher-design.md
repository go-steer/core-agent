# Self-development soak: the minimal dispatcher (A7)

**Status:** implemented for A7 ([#1213](https://github.com/go-steer/core-agent/issues/1213), v3.0 box A7 in [#1042](https://github.com/go-steer/core-agent/issues/1042)). The parent design is [`selfdev-soak-design.md`](selfdev-soak-design.md). This note covers only what the dispatcher at `dev/uat/selfdev-soak/dispatcher` does and the choices made writing it. The parent's decisions are not restated.

## Problem

Phase 2 of the soak design needs a dispatcher that runs steps 0–3 and 7 of "The dispatcher". It pauses on `soak:pause`, polls the mirror for maintainer-queued issues, hands one to the daemon, and pushes the agent's local commits as a PR with the writer App's token. On a cap or halt it stops the issue. That is enough to run A7: one seeded issue, end to end, with no person in between. Steps 4–6 (re-waking a session on red CI, review comments or a stale branch) and 8 (the nightly harvest) are for the 2-week soak and come later.

## Shape

```
poll (2m) ── soak:pause open? ── yes ──▶ hold
   │ no
   ├── reap: tracked PR closed/merged ──▶ remove its working copy
   ├── active issue in state file? ──▶ resume the watch (never re-inject)
   ├── open agent/* PRs ≥ cap? ──▶ hold
   └── oldest claimable soak:queue issue that passes decision 6
          │  save state, label soak:active
          ▼
   private bare repo ◀── fetch --depth=1 main ── mirror (App token)
          │ clone --depth=1 (file://)
          ▼
   <worktrees-dir>/issue-N  (branch agent/issue-N, soak identity in local config)
          │ POST /sessions, GET /events, POST /inject
          ▼
   session idle ── trip / turn error / timeout / no commits ──▶ stop (step 7)
          │ clean
          ▼
   fetch agent/issue-N back into the private repo ── verify identity ── push SHA ── open PR
```

`--once` runs this for exactly one issue, to a PR or a stop, then exits. The A7 run uses it. It exits 0 for a PR and 1 for a stop, and also 1 when a signal ends the run before either.

## Settled decisions (do not relitigate)

1. **A Go program in the main module, reusing in-tree clients.** It is `dev/uat/selfdev-soak/dispatcher`, a `main` package, built, vetted, linted and tested with everything else. It talks to the daemon through `internal/attachclient`, reads the durable rows with `pkg/attach`'s own readers (`GuardrailHaltRow`, `GuardrailTurnTrip`, `TurnErrorRow`), reads the attach token with `childenv.TakeFile`, and reads the session's plan artifact with its own link-refusing reader (decision 16). GitHub is a dozen hand-rolled REST calls. The App JWT is built with the standard library, so no new dependency comes in.
2. **Provenance comes from the issue's event history, and it is strict.** The issue must be authored by the maintainer. It must have at least one `labeled soak:queue` event and at least one `assigned` event, and **every** such event must be the maintainer's. For an `assigned` event, both `actor` and `assigner` must be the maintainer, because older payloads used `actor` for the assignee. In practice, the maintainer assigns the issue to themselves. Every `renamed` event must be the maintainer's too, because the title is part of the task. One `soak:queue` label applied by anyone else disqualifies the issue for good: removing it and re-applying it does not launder it. Logins and label names compare case-insensitively, as GitHub does, and a missing actor (a deleted account) never matches. Every events page is read. A history longer than the page bound is an error, never a truncated pass.
3. **The claim is the `soak:active` label, not an assignment to the bot.** The maintainer's assignment is the go-ahead decision 6 reads. The dispatcher marks a taken issue with `soak:active`, and drops it for `soak:stopped` on a stop. The dispatcher never assigns anything. An App's bot account can't be relied on as an issue assignee, and GitHub drops an assignee it won't accept without an error. Worse, the dispatcher's own `assigned` event would carry the App as its actor, and decision 6 would then refuse the issue for good when a person retried it.
4. **A pause needs no provenance.** Any open issue labeled `soak:pause` holds the dispatcher, whoever wrote it. Pausing is the safe direction. The pause is checked before every claim and again before every push, so a pause that lands mid-issue holds the push as well.
5. **The working copy is a fresh shallow clone, not a `git worktree`, and credentials live in a private repository.** A linked worktree shares its `.git` with the repository it came from. The agent can write that `.git`, so every later dispatcher git command there would run whatever it planted: a hook, a `core.fsmonitor` command, a filter driver. Those would run in the dispatcher's pod, next to the App key. Instead:
   - the dispatcher keeps a bare repository the agent can't see (`--private-repo`). The App token only ever touches that repository.
   - each issue's copy is a `--depth=1` clone of the base tip from it, so nothing that was ever in the mirror's history is in reach (decision 20).
   - after the session, the branch is fetched back into the private repository and verified and pushed from there.

   The only process that runs inside the agent-writable copy after the agent has had it is the `upload-pack` serving that fetch. Every git call also pins `core.hooksPath=/dev/null`, `core.fsmonitor=false` and `protocol.ext.allow=never`, and clears `credential.helper`.
6. **The token reaches git through a 0600 file, never argv or the environment.** For each fetch or push, the installation token is written to a 0600 file in a fresh 0700 directory under the dispatcher's `TMPDIR`. Git reads it through the stock `store` helper, and the directory is deleted afterwards. The App key is mode-checked like a token file and never echoed. Reading the attach token through `TakeFile` makes the process non-dumpable.
7. **The verified SHA is pushed, never the branch, and never with force.** Pushing `<sha>:refs/heads/agent/issue-N` means a commit the agent adds after verification never goes out. A remote branch left over from an earlier attempt rejects the push. The issue then stops, and its branch is not overwritten.
8. **Identity is checked on every commit past the base (decisions 8 and 16), read from the raw commit object.** Each commit is read with `git cat-file commit`, not from a `git log --format` rendering. Git accepts any byte in a name or a message, so separator bytes in a format string can be forged: a record separator in a message hid a `Co-authored-by` trailer in the first draft. The object has one header per line and no header value can hold a newline, so it can't be forged that way. A control byte in an identity or a message is refused outright, and trailers are scanned on every line ending, including a bare carriage return. The author and committer must both be the configured soak identity, compared by exact name and case-insensitive email. There must be at least one `Signed-off-by`, and every sign-off must name the soak identity. Any other credit trailer (`Co-authored-by` and the rest of the set `verify-no-agent-attribution` scans) is refused, as is any `[bot]@` or noreply address. A configured identity that could never pass fails at startup. The dispatcher sets the identity in the copy's local git config, so the agent's plain `git commit -s` produces it.
9. **"Idle" means a turn ended, the session reports idle, and it has stayed quiet for the settle window.** The event stream is opened *before* the inject, because `turn-complete` is a live-only frame. A turn has ended once a `turn-complete`, a `turn-error` frame or a durable `turn-error` row arrives. After that, `GET /status` must say `idle` with no turn in flight, and no activity may arrive for `--settle` (30s). The settle window covers auto-continue starting another turn. A dropped stream reconnects with `since=<last seq>`, so trip and turn-error rows are replayed, not missed. A `turn-complete` lost in that gap can't be replayed. After a reconnect, evidence that a turn ran is enough, combined with the settled idle status. That evidence is a non-idle `status-update` or a model-authored row. The same holds after `--start-timeout` of quiet, for a stream that died without closing. A turn error followed by later model output is not the session's last word, so a replay doesn't stop an issue over an error the session recovered from. A session that never ends a turn within `--start-timeout` stops the issue, because a refused turn puts no frame on the wire.
10. **Any guardrail trip stops the issue, even when the agent committed.** That covers both the halt and the per-turn trip, read from the typed frame or the durable row and counted once by event ID. A7's "ended by work" excludes a ceiling or a halt. A last turn that ended in an error stops it too. A session still running at `--session-timeout` is interrupted and stopped.
11. **A stop is written down before GitHub is told, and its comment can't wedge the queue.** The reason is capped at 2000 bytes, because part of it can be agent-controlled (a turn error's message, a commit header) and GitHub refuses a comment over 65536 characters. The reason goes into the state file first. Then the dispatcher interrupts the session (on every stop path, before the copy goes), labels the issue `soak:stopped`, removes `soak:active`, and deletes the copy. A label failure is retried on the next poll. The comment is queued in the state file and posted last. A failed comment is retried on later polls (up to 10 times) without holding the labels, the cleanup or the next issue. The dispatcher never retries the issue itself (decision 17). The stop comment says that removing `soak:stopped` re-queues it.
12. **Restarts resume, never inject twice, and never open a second PR.** A state file holds the active issue and the open PRs. `Injected` is saved before the inject call. A restart before that point gives the issue back to the queue: nothing was attempted, so there's no stop to hide. A restart after it resumes watching the same session, and replays from seq 0 so trips that happened while the dispatcher was down are seen. Before it opens a PR, the dispatcher looks for an open PR on the branch and adopts it. That covers a crash after a PR opened but before the state file recorded it. `--state-file` is required and has no `/tmp` default.
13. **The whole inject counts as the task, and `injectTask` is the P1 hook.** No `task_bytes` is sent. The issue text comes first, and the rig's fixed instructions follow it: the branch, `-C` addressing, stop at local commits. The approver should judge calls against both, and the dispatcher is the listed `task_from` caller. The text carries only the issue's title, body, number and upstream link, plus the rig's own instructions. It never carries labels or other issue metadata (decision 20). `taskInput` has no field for them. P1's standing-task flag gets set in `daemonClient.injectTask`, and nowhere else (decisions 15 and 19).
14. **The agent is told where its copy is, because a session can't be given a working directory.** `POST /sessions` has no working-directory field. The task names the copy's path and tells the agent to use `git -C` and `go -C`, one command at a time, because a compound `cd … &&` never matches an eligible prefix.
15. **A missing upstream link stops the issue before any session exists (decision 12).** The stop is visible, so the queue never skips an issue silently.
16. **The plan artifact is read without trusting the agent-writable directory.** The PR body quotes the session's newest active plan from `--agents-dir`/plans. That directory is the agent's to write, and the dispatcher reads it in its own pod, where a symlink would resolve to the dispatcher's files, the App key included. So the reader skips `tools.ActivePlans`, which follows links and reads without a bound. A symlinked `plans` directory is ignored. Each file is opened with `O_NOFOLLOW|O_NONBLOCK`, must be a regular file, and is read once with a bound. The frontmatter's session is checked on the same bytes that get published.
17. **The dispatcher's own `/events` subscription is an attach client.** A7's "no human" assertion has to exclude the dispatcher's identity (`sa:selfdev-dispatcher`) when it counts attach clients. Any other client during the run is still a failure.
18. **git's output about the agent's copy never reaches a message.** Git echoes the content of files it fails to parse, including `objects/info/alternates`, `packed-refs`, `info/grafts` and an included config. The agent can point any of those at a file in the dispatcher's pod, the App key included, and the fetch-back runs `upload-pack` there. So every git command on the fetch-back path discards its output (`runQuiet`), and its error carries only the exit status. That output never appears in a stop reason, log line, comment or the state file. Before the fetch, `inspectCopy` refuses a copy whose `.git` is not a real directory, or contains a symlink or a special file, or has `objects/info/alternates`, `http-alternates`, `info/grafts`, `commondir` or `gitdir`, or a `shallow` file naming anything but the base. It also refuses a config (`config`, and `config.worktree` if present) that is larger than 64 KiB or contains, ignoring case and whitespace, an include section, `partialClone`, `promisor`, `uploadpack`, `receivepack` or `worktreeConfig`. The fetch runs with submodule recursion off. Every git process runs with `GIT_NO_LAZY_FETCH=1`. Without that, a copy set up as a partial clone could make `upload-pack` lazily fetch from the agent's promisor remote and run its `uploadpack` command. Git only sets it itself from 2.45.1 (and the 2.39.4 backport), and the soak image's Debian git is 2.39.x.
19. **A stale ref is deleted before the fetch-back.** A fetch that declines to update a ref (a shallow-root rejection, when the agent appends its tip to `.git/shallow`) warns and exits 0. So `refs/soak/issue-N` is deleted first, and a fetch that doesn't recreate it is a stop.
20. **Background subagents keep the session busy.** `/status` reports idle whenever the parent has no turn in flight. An async subagent, such as the self-recipe's reviewer (up to 30 minutes), is invisible there, and when it finishes it wakes the parent for another turn. So each poll also reads `GET …/agents`. The session isn't done while any subagent is running or deferred, and any change in the subagent list counts as activity for the settle window. A failed read counts as busy.
21. **Decision 6 also covers body edits, reopening, retries and Apps.** Body edits come from one GraphQL `userContentEdits` call with the installation token. Every editor must be the maintainer. An edit GitHub can't attribute, or more than 100 edits, is refused. Reopening the issue, removing `soak:queue`, and removing `soak:stopped` (a retry, which decision 17 reserves to a person) must also be the maintainer's. No issue, and no event that carries authority, may have `performed_via_github_app` set. The dispatcher's own `soak:active` and `soak:stopped` labels carry no authority, so they don't make a retried issue ineligible.
22. **Agent text can't close issues or carry attribution.** Closing keywords in the plan text quoted in the PR body are rewritten to `refs`, so merging closes only the dispatcher's own `Fixes #N`. A commit whose closer targets any other mirror issue is refused. A closer aimed at another repository, such as the upstream issue, is left alone. The text rules of `verify-no-agent-attribution` are ported: banned trailer keys such as `Self-Development-Run:`, and the "Generated with <agent>" and robot footers. They apply to every commit and to the final PR body. A plan that fails them is withheld from the body. A soak identity whose name is an agent's (`core-agent`, `claude`, …) fails at startup.
23. **The state file is fsynced.** The temp file is synced before the rename and its directory after, so a node crash leaves either the old state or the new one.
24. **The copy gets release tag names, and nothing behind them.** The presubmit sweep's `verify-version-fallback` fails with "no release tags found" in a copy that has none. That would give the agent a red check it can do nothing about, and a run could end on chasing it. The check reads only the names from `git tag --list 'v*.*.*'`, sorted by name. It never runs `git describe`, never tests reachability, and never reads what a tag points at. So the copy needs tag names that resolve, and nothing more. Decision 20 bounds what crosses:
    - **Where the tags come from.** `fetchBase` fetches release tags by name from `--tags-remote`, with no credential, into `refs/upstream-tags/` of the private repo. The default is the public upstream repository, because the mirror isn't guaranteed to carry tags. `fetchBase` also fetches the base's full history into the private repository. That history never reaches a copy. A private repository left depth-1 by an earlier dispatcher is unshallowed on its next fetch.
    - **Which tags cross.** Only `refs/tags/vX.Y.Z` tags (no pre-releases), and only those `--merged` into the copy's base, as evaluated in the private repo. A tag after the base could point at the fix the issue asks for, or name the version that shipped it.
    - **No historical object crosses.** Every copied tag points at one placeholder blob that the dispatcher writes into the copy. The blob's text explains what the tag is, so `git show vX.Y.Z` explains itself. The real objects are not copied:
      - a release's commit message is older repository text, and a GA cut on the wrong commit would carry, say, a message about the seed list into every copy;
      - its tree is an older state of the repository, and could still hold the seed list itself.
      - Copying a tagged commit without its tree was tried first. It left commits whose trees were missing, and `git show`, `git diff vX.Y.Z`, `git gc` and `git fsck` all failed in ways that look like repository corruption.
    - **What the blob tags change.** A tag that points at a blob is ignored by `git describe` and by Go's VCS stamping. `git log --all`, `git gc` and `git fsck` stay clean. The copy gains no remote, no history and no shallow root, so `inspectCopy` is unchanged. `git diff v2.9.0` fails, which is accurate: the release isn't in the copy.
    - **A copy that no release tag reaches is refused.** It stops the issue with a reason naming `--tags-remote`. Otherwise it would silently reproduce the red check. This happens when the tags remote shares no history with the mirror, for example after a squash-synced mirror or a wrong flag.
    - **A failed tag fetch is a failed `fetchBase`.** Like a failed mirror fetch, it stops the issue (decision 17: a person retries).
    - **Before the agent sees the copy.** All of this runs before the agent has the copy. `GIT_NO_LAZY_FETCH=1`, the hardening `-c` flags and the copy checks are unchanged.
    - **No tag object rides along with the clone.** The private repo keeps the fetched tags under `refs/upstream-tags/`, not `refs/tags/`. A clone sends the annotated tag object of every `refs/tags/*` entry that points at a commit it sends (include-tag, even with `--no-tags`), which would have put the message of any annotated tag on the base, a pre-release included, into the copy. `git fsck` in a copy reports no dangling tag.
    - **The note names no place to read history.** The public upstream repository's history still holds the seed list, so the note must not point there. A worker with GitHub egress could still reach upstream without a hint. That gap predates this decision and lies outside the copy; it is tracked separately from this change.

## Where steps 4–6 and 8 attach

- **Steps 4–6** (re-wakes for CI, review and rebase) extend `reap`. That loop already visits every tracked PR on every poll. `openPR` keeps the session path and base SHA for this purpose. A re-wake injects into the same session and then reuses `publish`'s collect, verify and push. A non-forced push of a follow-up commit is a fast-forward. Step 5's comment forwarding needs its own provenance check, in the style of `checkProvenance`, for the reviewer and maintainer logins.
- **Step 8** (the harvest and archive) is a separate scheduled job over the eventlog and the PVCs. It does not belong in this process's loop.

## Deployment requirements

- **Shared paths and UID.** The daemon and dispatcher pods mount the workspace volume at the same path, because the task names the copy's path. They run as the same UID, so the agent can write the copy the dispatcher made.
- **The dispatcher's own volume.** `--private-repo`, `--state-file` and `TMPDIR` must be on a volume only the dispatcher pod mounts. `--state-file` must survive a pod restart, or the active issue is lost and stays `soak:active`, so put it on a PVC. The private repository can be rebuilt from scratch.
- **Optional plan lookup.** `--agents-dir` points at the daemon's `.agents` directory as the dispatcher sees it. Without it, the PR says the session recorded no plan.

## What the maintainer creates by hand

- **The writer GitHub App,** owned by the maintainer's account:
  - repository permissions: Contents read & write, Pull requests read & write, Issues read & write, Metadata read;
  - no webhook, and no other permissions;
  - installed on `mastersingh24/core-agent-selfdev` only (Install App → Only select repositories).

  Note its App ID and generate a private key. The key goes into a Kubernetes Secret mounted only in the dispatcher's pod, with `defaultMode: 0400`, and its path is passed as `--app-key-file`. The installation ID is discovered; `--installation-id` skips the lookup.
- **The mirror's labels:** `soak:queue`, `soak:pause`, `soak:active` and `soak:stopped`. To queue an issue, write it, label it `soak:queue` and assign it to yourself, all from the maintainer account.
- **The dispatcher's attach identity:** a `users.json` entry for `sa:selfdev-dispatcher`. Its token is mounted into the dispatcher's pod as a file and passed with `--token-file`.
- **The soak's commit identity:** a human-looking name and email for `--commit-name` and `--commit-email`. It is named in the mirror's attribution allowlist, never upstream's (decision 16 as amended).

## Out of scope

- Steps 4–6 and 8, above.
- P1's standing-task flag, and P2's hashed bearer tokens.
- **Comments on the issue.** The task never includes them; only steps 4–6, which aren't built yet, will forward any, and only from the reviewer and the maintainer.
- More than one issue at a time, and self-selection from the queue (v2).
- The Dockerfile, the kustomize overlay, and the seed script (phase 2's other pieces).
- Deleting remote `agent/issue-N` branches. A person retrying a stopped issue deletes its old branch first.
